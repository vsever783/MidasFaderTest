# MidasFaderControl

Android-приложение для удалённого управления микшерным пультом **Midas Pro2** по протоколу Pro2/PPC поверх UDP (OSC-подобные сообщения). Один APK, два режима:

- **Engineer (инженер)** — полный контроль пульта с планшета: все каналы, master, aux-возвраты, aux-шины, VCA, матрицы (Main Outs).
- **Monitor (музыкант)** — упрощённый режим с телефона: посылы своего канала в выбранную мониторную шину + громкость шины. Лёгкий набор подписок (~64 параметра), чтобы не мешать другим подключённым приложениям.

Протокол реверс-инжинирен с нуля (у Midas нет открытой документации на Pro2/PPC) — путём сравнения трафика официального приложения **Mixtender 2** через Wireshark, а также сверки с открытым датасетом сообщества (см. раздел «Источники данных»).

---

## Архитектура навигации

Три экрана в строгой последовательности:

```
ConnectActivity → RoleSelectActivity → MainActivity (Engineer | Monitor)
```

- **ConnectActivity** — ввод IP/порта пульта, устанавливает UDP-сокет (локальный порт `10001`, пульт слушает `10000`). Больше ничего не делает.
- **RoleSelectActivity** — выбор режима (Engineer/Monitor). Передаёт режим в `MainActivity` через `Intent extra`.
- **MainActivity** — сам интерфейс, в двух режимах (`appMode`).

### Важно: соединение переживает переключение режимов

Раньше (до одного из последних крупных рефакторингов) переключение между Engineer и Monitor полностью пересоздавало UDP-сокет и слало заново все ~800 подписок — это перегружало пульт и сбивало официальный Mixtender при частых переключениях.

Теперь:
- Сокет/сессия хранятся в **`ConnectionHolder`** (singleton) и создаются **один раз** в `ConnectActivity`.
- `MainActivity.onDestroy()` при возврате к выбору режима делает **лёгкую** отписку (`/unsubscribe` только для подписок текущего режима) — сокет **не закрывается**.
- `MainActivity.beginModeSession()` при входе в режим **переиспользует** уже живой сокет, просто подписывается заново под конкретный режим.
- **Полное** отключение (закрытие сокета, `ConnectionHolder.reset()`) происходит только в `RoleSelectActivity.onDestroy()` — когда пользователь уходит даже оттуда (кнопка «назад» до экрана подключения, либо закрытие приложения).
- Различение «это поворот экрана» vs «свежий вход в режим на живом соединении» — через флаг `ConnectionHolder.subscribedAlready`.

## Протокол — ключевые факты

- Транспорт: **UDP**, OSC-подобные сообщения (не совсем стандартный OSC).
- Подписка на параметр: `/batchsubscribe (handle, fullPath, arg1, arg2, token)`. Хендл — произвольная строка вида `/h_{sessionId}_{channel}_{param}`.
- Живое обновление приходит в OSC-бандле как `,bi` (blob=значение в LITTLE-ENDIAN байтах, int=токен).
- `/renew` каждые 3 сек держит подписку живой (без этого пульт её забывает).
- Полный адрес параметра: `/{enPPCTypeMessage}/{enVirtualGroup}/{enParamName}` — например `/enPPCRotaryMessage/enVirtualMicInputs/enInputGain`.
- **Toggle-параметры** (`enPPCSwitchMessage`): почти все ведут себя как *переключатель по факту получения пакета* — значение аргумента не важно, реальное направление (вкл/выкл) определяет сам пульт. Подтверждено датасетом (`README` в `muffeeee/midas-pro-series-osc-commands`): «nearly all `enPPCSwitchMessage` — toggles, sending 1 toggles the switch». Известные исключения (`isAbsolute: true`, честно принимают 0/1): ножные переключатели (`enFootSwitch1/2`), `enCompLimKnee` у мастера и микрофонных входов.
- Отписка: `/unsubscribe(handle)` — **раньше в приложении не вызывалась вообще**, что приводило к разбуханию таблицы подписок пульта при переподключениях. Теперь вызывается всегда перед новым подключением/при выходе из режима.

### Байтовый порядок — важная деталь

Push-обновления от пульта (значения) идут в **LITTLE-ENDIAN**. Команды `/set`/`/get` (то, что шлём мы) — обычный OSC big-endian. Несогласованность в самом протоколе, не баг с нашей стороны.

## Что реализовано и подтверждено реальным трафиком

- Fader, mute, solo, gain, pan, phantom (48V), phase, имя канала, цвет (RGBA), живые метры
- Compressor (ratio/attack/release/threshold/makeup/in) — калибровочные таблицы **подтверждены датасетом**, совпали с ранее подобранными вручную
- EQ 4 полосы (bass/low-mid/mid-high/treble): freq/gain/width/on-off, форма bass/treble — **4 режима** (PARAMETRIC/BRIGHT/CLASSIC/SOFT), не просто bell/shelf
- Gate (threshold/range/attack/hold/release/transient/filterFreq/in/filters)
- HP/LP фильтры входа
- VCA-группы: fader/mute/solo/имя/цвет + **членство каналов** (полностью подтверждено реальным захватом — адреса `enVCAChildInput/SubMix/AuxReturn/Main/MasterL/R/C`)
- Master, Aux Returns, Aux-шины (Sub Mixes) — базовые параметры полосы
- Main Outs (матрицы) — базовая полоса + LINK (`enConfigPairingState`, подтверждено, работает)
- Global TAP (`enGlobalTapSwitch`) — **не подтверждено**, кнопка есть, эффекта на пульте пока не заметили
- Патчинг (`enChannelSource`, `enVirtualMicInputs`) — параметр найден, но **кодировка значения не расшифрована** (не 1:1 номер входа, похоже на составное число «тип устройства + номер канала»)

### Калибровка (перевод сырых 0.00–1.00 в реальные единицы)

| Параметр | Диапазон | Источник |
|---|---|---|
| Фейдер (все типы) | -∞…+10 дБ, унити на 0.75 | Кривая X32/M32 (Behringer/Midas общая инженерная база) — **не подтверждено для Pro2 конкретно** |
| EQ Gain | ±16 дБ | Подтверждено фото шкалы пульта |
| EQ Freq (bass/lo-mid/mid-hi/treble) | 16–400 / 80–2000 / 320–8000 / 1000–25000 Гц | Подтверждено фото шкалы пульта |
| EQ Width | 0.1–3.0 | Подтверждено |
| Comp Threshold/Attack/Release | см. код | Подобрано вручную, позже **подтверждено** текстом описания в датасете (точное совпадение) |
| Comp Makeup Gain | 0/8/16/24 дБ на 0/0.35/0.65/1 | Подтверждено текстом описания в датасете |
| Comp Presence | -100/-16/-8/-3 дБ на 0/0.35/0.65/1 | Подтверждено текстом описания в датасете |
| Comp Filter Frequency | 50/300/2500/15000 Гц на 0/0.35/0.65/1 | Подтверждено текстом описания в датасете |

| Gain / Gain Trim (преамп) | не откалибровано | Данных нет вообще |
| Pan | линейно, L/C/R в % | Не требует калибровки |

## Новая, ещё не проверенная на пульте территория

Найдено в датасете и/или реальном трафике `all config ipad.pcapng`, реализовано «на веру»:

- **Main Outs**: полный EQ (6 полос!), компрессор, HP/LP/notch фильтры, Presence, Bus Trim, три циклических режима (**STYLE**, **FILTER BANDWIDTH**, **KNEE** — существование и тип подтверждены, смысл цифр — нет)
- **Aux-шины**: LINK подтверждён работающим; EQ/компрессор реализованы по аналогии с Main Outs, но **ни разу не встречались подписанными** в реальных захватах — не факт, что физически существуют на этой модели
- **Mute-группы** — структура известна из датасета (`enMuteGroupChild*`, та же логика, что VCA), **не реализовано** (отложено пользователем)
- **Graphic EQ Pool** (31 полоса, `enGEQPool`) — отдельный большой инсерт-эффект, не привязан к каналу напрямую — отложено (это уже «эффекты», следующий этап после проверки основного функционала)
- **Internal FX** (~700 параметров, `pro-series-internal-fx-parameters-endpoints.json`) — вообще не разобрано

## Дизайн

Единый «консольный» визуальный язык — тёмная палитра, скруглённые карточки-панели вместо голого чёрного фона:

- `#000000` — фон страницы, `#151517`/`#17171a` — карточки, `#1c1c1e`/`#2c2c2e` — заголовки/бейджи
- `#ff9f0a` — акцент (везде: заливка фейдера, активные состояния, значения)
- `card_panel_background.xml`, `console_button_background.xml`, `console_input_background.xml`, `channel_strip_card_background.xml`, `channel_header_badge_background.xml`, `big_action_button_background.xml` — переиспользуемые drawable-скругления

**Важный технический момент**: кнопки, которые красятся кодом через `setBackgroundColor()`, **теряют форму** (метод заменяет весь drawable на плоский цвет). Правильный способ — `backgroundTintList = ColorStateList.valueOf(color)`, красит поверх уже назначенного скруглённого drawable. Это грабли, на которые наступали несколько раз подряд (одиночные вызовы, многострочные вызовы, вызовы без явного receiver внутри `apply{}` — все три формата нужно ловить отдельно при поиске по коду).

### FaderView — кастомный компонент

`FaderView.kt` — вертикальный фейдер, рисует себя сам на `Canvas`, без старого трюка «`SeekBar` с `rotation=270` + подгонка ширины через `viewTreeObserver` под реальную высоту контейнера». Пропорции трека/колпачка считаются от реальной измеренной ширины вида (не от фиксированных dp) — одинаково хорошо выглядит на телефоне и планшете.

- Рифлёный нейтральный (серый) колпачок, цветная — только шапка канала
- Оранжевая метка унити (0 дБ) поперёк трека
- Шкала дБ сбоку — **реализована, но выключена по умолчанию** (`res/values/bools.xml` → `show_fader_scale = false`, `values-sw600dp/bools.xml` → `true`) — не проверялась на реальной узкой телефонной полосе
- Используется везде: главный экран (все типы полос), детальный экран канала, экран деталей aux-шин/Main Out, мониторный режим (полоса канала + посылы)

## Известные баги, на которые стоит обратить внимание при следующих правках

- **`android:scaleY="0"`** — старый способ анимации метра (через масштабирование), давно заменён на `layoutParams.height`, но атрибут несколько раз «просачивался обратно» в XML при восстановлении файлов после сбросов рабочей копии. Если метр где-то не показывается — первым делом проверить, нет ли scaleY=0 и правильная ли **начальная** высота (`0dp`, не `match_parent`) у вида метра.
- Рабочая копия проекта в среде ассистента периодически пересоздаётся с нуля из чистого архива — из-за этого случались случаи, когда уже сделанные ранее правки «терялись» и не были доставлены пользователю, хотя ассистент был уверен, что они уже применены. Стоит перепроверять фактическое состояние присланных файлов, если что-то выглядит нелогично.

## Структура проекта (основные файлы)

```
ConnectActivity.kt          — экран подключения (IP/Port)
RoleSelectActivity.kt       — выбор режима + чёрные системные рамки (applyBlackSystemBars)
MainActivity.kt             — весь основной интерфейс (оба режима), ~4700 строк
MainActivityNetwork.kt      — сетевой слой (extension-функции над MainActivity)
Pro2Commands.kt             — все OSC-адреса и кодирование команд
Models.kt                   — data-классы состояния (ChannelData, ParamKind и т.д.)
ConnectionHolder.kt         — singleton, переживает пересоздание Activity
OscUtil.kt                  — кодирование/декодирование OSC-сообщений
RotaryKnobView.kt           — кастомная крутилка (пониженная чувствительность — 750px на весь диапазон)
FaderView.kt                — кастомный вертикальный фейдер
EqCurveView.kt               — интерактивный график EQ канала (bell/shelf, HP/LP зона среза)
TransferCurveView.kt        — график компрессора/гейта

res/layout/
  activity_connect.xml
  activity_role_select.xml
  activity_main.xml          — главный экран инженера
  activity_monitor_connect.xml / activity_monitor_bus.xml — мониторный режим
  channel_strip.xml          — полоса канала (переиспользуется для всех типов через buildSimpleStrip)
  channel_strip_monitor.xml  — полоса канала в мониторном режиме
  channel_detail.xml         — детальный экран канала (INPUT/COMP/GATE/EQ/SENDS)
  group_detail.xml           — общий детальный экран aux-шины/Main Out (COMP/EQ)

res/values*/dimens.xml       — размеры под телефон (портрет/альбомная) и планшет (values-sw600dp)
res/values*/bools.xml        — show_fader_scale
```

## Источники данных

- **`muffeeee/midas-pro-series-osc-commands`** (GitHub) — основной справочник по адресам команд, включая файл `pro-series-internal-fx-parameters-endpoints.json` (~700 внутренних FX-параметров, не разобран).
- **`MyronKoch-dev/midas-pro-mcp-server`** (GitHub) — MCP-обёртка над тем же датасетом, отдельной ценности не несёт (тот же источник данных).
- **Реальные захваты Wireshark** (`.pcapng`) — основной способ подтверждения. Самый ценный — `all config ipad.pcapng` (287 уникальных подписанных путей). Важно: запись должна начинаться **до** открытия официального приложения/экрана, иначе не видно момента подписки с человекочитаемым именем параметра — видны только уже свёрнутые в числовые хендлы обновления.
- Фото экрана пульта — источник калибровочных диапазонов (шкалы EQ, компрессора).

## Открытые вопросы для следующих шагов

1. Расшифровать кодировку `enChannelSource` (патчинг) — нужен точечный тест: один канал, 2-3 известных источника по очереди, каждое переключение отдельно зафиксировано в записи.
2. Подтвердить существование EQ/компрессора у aux-шин на реальном пульте.
3. Разобраться со смыслом STYLE/FILTER BANDWIDTH/KNEE у Main Out — нужен захват с подпиской, сделанной ДО начала записи.
4. Проверить Global TAP — реагирует ли пульт вообще.
5. Калибровка Gain/Gain Trim/Comp Ratio — нужны либо фото шкалы, либо захват с известными значениями.
6. Реализовать Mute-группы (структура уже известна, по образцу VCA).
7. Дизайн мониторного режима — базово приведён к общему стилю, но не так тщательно, как инженерский.
8. Presence у компрессора — пользователь отметил как ненужный, кандидат на удаление из интерфейса.
